# 飞行控制代码开发、测试与优化闭环方案

日期：2026-10-03（UTC+8）  
状态：开发与迭代工作约定；不代表功能已实现或实飞已合格。  
配套文档：[无人机实飞验证与人机协同测试系统设计方案](flight_validation_design.md)。

## 1. 两份文档的分工

两份文档共同指导“写代码 → 测试 → 分析 → 修改或新增代码 → 再测试”，不把工作限制为验证已有逻辑，也不要求等到实飞失败才补充功能。

| 文档 | 负责内容 | 何时修改 |
|---|---|---|
| 测试系统设计方案 | 控制状态、功能范围、页面引导、操作步骤、准入、保护、结果和现场验收 | 用户可见行为、控制权、输入含义、测试流程或通过条件发生变化时 |
| 本闭环方案 | 需求如何转成代码、证据如何支持诊断、新功能如何验证、参数如何优化、版本与回归如何管理 | 开发和迭代方法需要调整时 |

测试系统设计方案是产品行为与现场流程的依据；本方案不另设一套飞行模式或保护门槛。文档出现冲突时，先按已确认的最新需求同步相关条款，不能让实现者自行选择有利于通过测试的解释。一般内部重构不需要改产品设计；改变输入含义、控制权或故障处理则必须同步。

统一用语只有：**程序主导、人工主导、完全接管**。首版只实现人工主导和完全接管，GPS 为观察项；程序主导及其降级留到第二阶段。具体控制语义遵循配套文档，不在此重新定义。

两份文档是工作依据，不是不可修改的最终结论。经验证不合理的逻辑可以修改、替换或删除；新发现的必要能力可以新增。

## 2. 迭代的输入：既可以是问题，也可以是新需求

每轮从一个明确问题或能力缺口开始，来源不限于试飞结果。

| 来源 | 示例 | 优先动作 |
|---|---|---|
| 代码审查 | 接管成功只看服务回执，没有确认实际模式 | 补充行为要求和失败场景，新增反馈确认逻辑 |
| 流程推演 | 页面断线后任务归属和收尾不明确 | 先确定状态迁移，再实现并故障注入 |
| 现有功能测试 | 摇杆回中后目标抖动 | 区分输入噪声、映射和平滑问题 |
| 控制响应测试 | 目标平顺但实际姿态持续振荡 | 对照飞控基线、反馈、饱和和机械条件分析 |
| 新增需求 | 希望每步自动汇总指标并显示原因 | 定义输入数据、结果语义和不可判定情况，再开发 |
| 参数证据不足 | 推力或超时沿用台架初值 | 建立标定项目，未合格前限制相关测试 |

问题清单可以很长，但一个迭代只围绕一个主要目标。强耦合的代码和参数允许作为一个变更组，必须说明为何不能拆开；不以“每次只能改一行”妨碍完整修复。

## 3. 每轮统一工作流程

### 3.1 明确预期行为

先写清楚触发条件、应发生的行为、不允许发生的行为，以及验证方式。功能不存在也能写出这些要求。

例如：“完全接管后，实际 PX4 模式退出 OFFBOARD；机载程序释放输出，不能自动重新进入 OFFBOARD。”这比“改一下退出逻辑”更容易实现和验收。

区分事实与假设：日志观察到什么是事实；为什么发生是待验证假设。不能把“可能是延迟”直接记成已定位原因。

### 3.2 建立基线与最小证据

- 已有功能：保存当前版本、有效参数、可复现步骤及观测结果。
- 新功能：记录“现有版本不支持”，以需求和行为测试建立初始基线，不要求人为制造实飞失败。
- 原始日志保留不变，分析结果另存；只提取本轮必要数据，避免无目的收集。
- 证据不足时先补观察点或测试，不急于调整控制增益。

### 3.3 选择变更类型

| 类型 | 适用情况 | 验证重点 |
|---|---|---|
| 修复 | 行为偏离已确认设计 | 原问题复现后消失，相关路径无回归 |
| 新增 | 缺少明确需要的能力 | 正常、边界、失败和退出行为均完整 |
| 替换/删除 | 既有逻辑不适用、重复或副作用过大 | 替代行为和依赖关系明确，不留下隐式分支 |
| 调参 | 逻辑和数据可信，但响应不达目标 | 同条件指标比较及保护门槛保持 |
| 重构 | 行为不变但可维护性不足 | 行为一致，避免顺便改变控制策略 |

不能用调参代替缺失逻辑，也不因参数暂时不佳就直接重写整个控制器。

### 3.4 定义验收，再实现

对控制、状态机、协议和数据判定，先定义能从外部观察到的输入/输出与结果；必要时先写能暴露问题的自动测试。测试不得只是复制实现内部算法后比较同一个结果。

新增功能同时定义失败行为，例如输入缺失、模式拒绝、命令重复、数据过期、程序退出。不能只实现成功路径，再把异常留给现场操作人员判断。

实现最小完整能力：包含主路径、必要保护、结果反馈及记录，不要求一开始搭建通用插件系统或自动调参框架。普通文字和低风险展示修改采用静态/页面检查，不为每次小改动强行增加自动测试。

### 3.5 按影响范围逐级验证

先使用能回答问题且风险最低的方法；上一级证据不足，不用实飞替代诊断。

| 验证层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 静态检查与单元测试 | 映射、限幅、状态转换、重复命令、结果判定 | 真实通信时延、飞行动力学 |
| 记录回放 | 原异常是否被识别、指标计算是否一致 | 修改控制器后真实飞机会怎样响应 |
| SITL/HITL | 交互、模式切换、故障时序及模拟闭环 | 真实结构、振动、推力和接触条件完全一致 |
| 拆桨台架 | 实际通道、接口、通信、模式确认及失联行为 | 悬停推力、真实姿态跟踪、水平制动 |
| 受保护动力试验 | 当前约束条件下的动力响应及交接 | 无约束自由飞行合格 |
| 自由飞行 | 指定环境和配置下的实际能力 | 所有载荷、环境和异常都可靠 |

涉及遥控/推力/姿态/模式输出的改动，至少完成针对性软件验证及适用的仿真、拆桨检查，才进入动力试验。没有仿真条件时如实记录验证缺口，不能把未执行写成通过。

### 3.6 对比与结论

对照事先确定的指标，不临时挑选改善的曲线。每轮结论固定为：

- **保留**：在已验证范围内达到要求且相关回归通过。
- **回退**：目标未达成或引入不可接受副作用。
- **继续调查**：证据不足，保留实验记录，不升级为合格基线。

代码完成、软件测试通过、受保护试验通过、自由飞行合格分别记录。不能用“已完成”隐藏尚未验证的层级。

## 4. 如何定位问题而不是盲目调参

优先按数据链定位异常首次出现的位置：

```text
实体遥控输入
  → 机载收到的输入及年龄
  → 映射/平滑后的目标
  → 唯一出口的最终设定值
  → PX4 接收反馈及控制状态
  → 实际姿态、角速度和运动
```

| 现象 | 首先检查 | 暂不应直接做的事 |
|---|---|---|
| 输入自身抖动或过期 | 接收机、采样、消息频率、死区及时间戳 | 提高姿态增益补偿 |
| 输入稳定而程序目标跳变 | 映射、参考重置、坐标转换、状态迁移 | 归因于 GPS 或飞控 |
| 程序目标正确但最终输出不同 | 输出所有权、限幅、交接及残留旧指令 | 只调上游目标参数 |
| 最终目标平顺而实际响应异常 | 实际飞控模式、反馈可信度、动力余量及原生基线 | 断言是机载程序或某个 PID 单独造成 |
| 页面显示异常而机载记录正常 | 遥测缓存、显示节流、时钟及数据年龄 | 修改飞行控制回路 |

源数据、目标数据和实际响应应使用可关联的时间及样本标识。不同设备时间未对齐时，只报告可测的局部延迟或范围，不推算精确单程延迟。

对硬件、估计器或环境导致的问题，可以形成配置修正或运行边界结论，不强行以增加代码作为每轮产出。

## 5. 新增逻辑的工作方式

新增能力不必依附某个已有参数。每次新增先回答：

1. 缺少什么能力，影响哪个测试或操作？
2. 哪些输入足以支持它，输入无效时如何处理？
3. 哪个模块负责，是否改变控制权、输出类型或操纵含义？
4. 如何证明效果，新增哪些失败场景与回归场景？
5. 如何在不用新功能时回到已知行为？

例如新增“交接推力匹配”：先定义目标来源、匹配条件、过渡输出、超时和失败处理；再覆盖匹配、不匹配、交接中动杆、反馈过期及完全接管。控制权确认与实际响应分别验收。不能通过关闭硬推力限制来获得表面上的连续性。

新控制行为默认不进入现场运行配置，先用明确的实验配置验证；不是要求增加大量功能开关。完成验收后形成单一正式行为，及时移除临时分支，避免旧逻辑和新逻辑长期叠加。

若新功能改变页面步骤或结果含义，同时更新测试系统设计方案与页面提示；若只是内部模块改造，更新本轮记录和必要的软件测试即可。

## 6. 参数优化规则

### 6.1 参数分组

| 参数类别 | 例子 | 修改约束 |
|---|---|---|
| 输入标定 | 通道、方向、端点、中位、死区 | 根据实测确定，不以飞行表现猜测通道 |
| 控制参数 | 目标变化率、推力映射、控制增益 | 一轮改变一个相关组，记录预期改善与副作用 |
| 完成判据 | 允许误差、稳定保持时间 | 依据测试目标，不为了让当前结果通过而放宽 |
| 保护门槛 | 超限停止、超时、活动边界 | 独立说明依据，重新验证对应故障场景 |
| 显示/记录参数 | 绘图频率、日志窗口 | 不影响实时控制，不冒充控制性能优化 |

### 6.2 比较条件

改参前落地上锁，生成新参数版本并保存有效值快照；明确固定的其他参数、载荷、电池状态和环境。不能把三个参数组一起改变后，把改善归因于其中一个参数。

如果环境或载荷不同，标记为不可直接比较，必要时重建基线。性能指标同时观察改善项和代价项，例如平滑程度改善时也检查输入延迟，而非单独追求曲线好看。

重复性要求沿用测试系统设计方案，不在这里另设次数或数值门槛。通过有限次数只能说明这些试验条件下可重复，不构成全部场景可靠性证明。

## 7. 基线、版本与回退

维护两类基线：

- **开发基线**：软件和适用的低风险验证通过，可继续开发；不代表可飞。
- **现场合格基线**：在明确硬件、参数和环境条件下完成对应现场项目，标明验证层级和范围。

每轮关联代码提交或源码差异快照、参数版本、飞控固件及相关参数、EXE/机载协议版本、测试项目和证据。未提交代码不能只记录一个 Git HEAD 而忽略本地修改。

不覆盖原始日志、不覆盖上次正式参数、不通过重置整个工作区撤销一项实验。回退明确指向本轮代码/参数变更，并保留用户其他修改。

远端更新只在未解锁、无活动任务时进行。部署后核对实际版本、有效配置和唯一输出实例；本机编译成功不等于远端已经运行新版。代码与协议不匹配时仅观察，禁止动作。

每次变更列出受影响的验收项目。通道/推力映射变化需重新验证输入及交接；状态机变化需重新验证控制权和故障路径；仅显示文字变化不要求重飞所有项目。

## 8. 首版实施批次

每个批次形成可演示、可检查的产物，测试伴随开发，不等全部控制代码写完才测试。

| 批次 | 开发产物 | 本批验收 | 尚不开放 |
|---|---|---|---|
| I01 观察与证据 | 独立 EXE/页面、共享连接设置、只读遥测、版本核对、机载记录 | 离线可打开；断线标陈旧；重连不重放；不产生控制输出 | 任何飞行动作 |
| I02 测试步骤与 RC | 步骤/结果模型、RC 标定、引导操作、事件证据关联 | 各轴方向/中位检查；过期与无效输入识别；每步能解释结果 | 带动力 OFFBOARD |
| I03 控制权与完全接管 | 人工主导状态机、唯一输出、地面抑制、原生模式接管、防重入 | 软件/仿真和拆桨验证；模式请求与实际反馈区分 | 未通过交接验证的动力试验 |
| I04 目标生成与响应分析 | 人工姿态/推力映射、限幅和平滑、目标到实测曲线、故障处理 | 坐标与边界测试；陈旧数据处理；生成受保护试验候选版本 | 程序主导及自动起飞 |
| I05 现场闭环 | 原生基线对比、受保护人工主导测试、参数版本比较、重复性汇总 | 按主方案 T05/T06/T07/T11 的适用步骤取得证据并逐项改进 | 未单独准入的自由飞行 |

I03 的输出验证先在仿真或拆桨条件进行；I04 控制目标实现和相关检查完成前，不因 I03 状态切换通过而开放动力试验。原生模式开关接管路径始终独立于机载程序。

首版完成后再进入第二阶段程序主导开发，不能因 GPS 观察结果良好提前启用尚未验收的程序起飞。

## 9. 每轮最小记录模板

每轮用一个简短 Markdown 记录即可，首版不建设复杂工单平台。建议保存到本包 `docs/iterations/`，原始大日志保留在已有记录目录，以路径或索引关联；日志不是设计文档附件的替代品。

```markdown
# ITER-编号：本轮目标

- 类型：修复 / 新增 / 替换删除 / 调参 / 重构
- 状态：待实现 / 开发中 / 待验证 / 保留 / 回退 / 继续调查
- 关联设计条款及测试项目：
- 原版本与参数版本：
- 现象或能力缺口：
- 已有事实与证据：
- 原因假设（未证实部分）：
- 预期行为、通过条件、停止条件：
- 本轮变更与保持不变的条件：
- 新增/修改的测试及相关回归：
- 实际执行环境与验证层级：
- 结果与指标对比：
- 未执行项及原因：
- 结论、适用范围与回退方式：
- 下一步：
```

每次现场执行另记录 session/test/attempt ID。同一代码迭代可包含多次测试，但每次结果独立保留；测试失败不必立刻改代码，先判断是否可复现及证据是否足够。

## 10. 每轮结束与下一轮开始的条件

一轮结束不意味着所有飞行能力都已解决，而是本轮已有明确结论：变更了什么、做过哪些验证、证据支持到什么范围、剩余问题是什么。

进入下一轮前检查：

1. 本轮实际行为与相关设计条款一致，或差异已明确记录并修订。
2. 应完成的验证已执行，失败/中止/无法判定没有被隐藏。
3. 保留或回退决定明确，基线和参数版本可恢复。
4. 新风险、受影响项目和未验证范围可被下一位开发者或操作者理解。
5. 下轮只选择当前最需要解决的一个问题，不为追求进度同时扩大动作、放宽门槛和调整多个控制组。

当前工作从 I01 开始。建立可靠的观察、记录和结果反馈之后，再逐批增加控制能力；整个过程中允许依据证据新增或替换设计，而不是只对既有参数反复试值。
